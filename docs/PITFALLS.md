# 踩坑记录

这个项目里，**每一个"模型能力不足"的现象，最后都证明是数据或代码的 bug**。以下 14 条按"会浪费你多少时间"排序，每条都有现象、根因、修法。

想复现的人建议先读一遍——能省两天。

---

## 1. SFT 标签位移两次 → 生成跳字乱码（最难查）

**现象**：SFT loss 正常下降（1.07），但生成全是垃圾：

```
{"":topf",args{""pth":buil"}}
```

字符错位、key 名和引号乱飞，看起来像模型太小或训练崩了。

**根因**：`trainer/data.py` 里 `SFTDataset` 在 `__getitem__` 做了 `ids[:-1], labels[1:]` 的右移，但保存到 `sft.pt` 时存的是 **已经右移过的** `ds.items`。训练时 `SFTDataset` 又移了一次，模型变成"用位置 t 预测 t+2"，学的是跳字。

**修法**：`sft.pt` 必须存**未右移**的原始 `(ids, labels)`，位移只发生在 `__getitem__`。

```python
# 错误：torch.save({"items": ds.items})          # 已右移
# 正确：
raw = [(ids[:max_len], lab[:max_len]) for ids, lab in items]
torch.save({"items": raw, "pad_id": tok.pad_token_id or 0}, out)
```

**教训**：位移这类"全局偏移"的 bug，loss 曲线完全正常，只能靠**解码一条样本肉眼比**发现。分词后一定要打印还原样本。

## 2. 标签完全没位移 → 模型学成复读机

**现象**：loss 迅速掉到接近 0，推理时无限重复上一个 token。

**根因**：第一阶段忘记右移，模型被训练成 `f(x_t) = x_t`，也就是恒等映射。

**教训**：loss 掉得"太顺利"（< 0.3）要立刻怀疑标签错位。正常 SFT 的验证 loss 在 0.95–1.1 区间。

---

## 3. `<|end|>` 漏进自由文本，把 JSON 截断

**现象**：工具调用 JSON 只生成一半就停了，解析失败；或者回答里突然冒出 `build/app.log<|end|>`。

**根因**：`<|end|>` 在词表里 id=10，但它**不在** tokenizer 的 `all_special_ids` 里（因为它是 added token 而非标准 special）。自由文本段只排除了 `all_special_ids`，于是模型可以在任意位置生成它。

**修法**：按形状兜底，凡是 `<|...|>` 形态的都排除：

```python
if re.fullmatch(r"<\|[^|]*\|>", tok_str):
    logits[i] = -inf
```

**教训**：不要相信 tokenizer 的 `all_special_ids`，自己维护一份协议 token 列表并显式检查。

---

## 4. Git Bash 把 `</s>` 变成路径写进词表

**现象**：词表训完，eos 是 `None`，协议 token id 全部错位。

**根因**：在 Git Bash（MSYS）里执行 `--special-tokens '</s>'`，MSYS 把看起来像路径的 `</s>` 转成 `<C:/Program Files/Git/s>` 再传给 Python。

**修法**：`tokenizer/build_vocab.py` 把协议 token **硬编码在脚本里**，不经过 shell：

```python
SPECIAL_TOKENS = ["<s>", "</s>", "<unk>", "<pad>", "<mask>",
                  "<|user|>", "<|assistant|>", ..., "<|end|>"]
```

**教训**：任何会被 shell 当作路径/通配符的字面量，都不要从命令行传。Windows + Git Bash 环境尤其。

## 5. 约束解码反而让准确率下降（反直觉，但真实）

**现象**：实现了逐 token 的语法约束解码（保证输出 100% 合法 JSON、工具名一定在表里），结果参数全对率从 99.5% 掉到 92%。

**根因**：强制字面量的逐字符推进，破坏了模型原生的 tokenization。模型本来一次输出 `"build/app.log"` 一个 token，被拆成逐字符后，每个位置的上下文都是没见过的形状，概率分布被切碎。

**修法**：改成**自由生成为主，约束解码兜底**：

```
自由生成 → 解析 → schema 校验 → 失败才用约束解码重生成
```

**教训**：结构约束不是免费的。约束保证的是"合法"，牺牲的是"准确"。在小模型上这个 trade-off 经常是负的——先测，再决定要不要开。

## 6. 预训练分词量估算偏差 40%

**现象**：目标 800M token，第一次跑完只有 550M。

**根因**：抽样步长按"3 字节/token"估算，但中文 byte-level BPE 实际是 **4.7 字节/token**（1.9 字/token × 2.5 字节/字）。估算偏小 → 每次抽样取的量不够。

**修法**：按 6 字节/token 保守估，并在 `train_all.py` 里加自愈：产出不足就按比例放大目标重跑。

**教训**：中文的 token/byte 比和英文差很多，任何按字节估 token 的地方都要实测校准。

## 7. 数据耦合：工具只见过一种文件类型

**现象**：`truncate_file` 在评测里全部失败，`find_name` 总是把内容关键词当文件名（`find . -name TODO`）。

**根因**：合成时文件池是全局轮转的。`truncate_file` 的模板恰好总轮到 `.log`，模型从没见过 `truncate .bin`；`find_name` 的 `pattern` 参数从内容池取值，学到了"找 TODO 就是找名字叫 TODO 的文件"。

**修法**：文件池按工具语义分池轮转——截断类轮 `logs/bak/txt`，查找类按 `name` / `ext` / `content` 各自分池。参数取值也按语义分池。

**教训**："随机"不等于"覆盖"。合成数据要按**语义维度**检查覆盖度，而不是看总条数。

## 8. 意图模板把答案写在问题里

**现象**：`python_run` 在评测里永远只生成 `code: "10"`，而正确结果是 `print(2**10)`。

**根因**：训练样本长这样——

> 用户：执行这段 Python：**print(2\*\*10)**

代码原文就在指令里，模型只学会了**从用户话里复制代码**。真实用户说"算一下 2 的 10 次方"时，话里没有代码可抄，模型就只能吐个 `10`。

**修法**：`tools/extra_sft.py` 补 108 条"自然语言 → 代码"样本，36 种计算 × 3 种问法，`code` 参数用真跑的 `python -c` 结果校验。

**教训**：如果模板把答案的一部分写进了输入，模型学到的就是复制，不是推理。**合成数据的模板必须像真实输入一样"缺信息"。**

## 9. 沙箱路径拦截被 shlex 绕过（安全漏洞）

**现象**：验收时 `del C:\Windows\System32` 没有被拦截。

**根因**：`shlex.split(cmd, posix=True)` 会按 POSIX 规则把反斜杠当转义符，`C:\Windows\System32` 被切成 `C:WindowsSystem32`，于是 `^[A-Za-z]:[\\/]` 的 Windows 绝对路径正则匹配不上。

**修法**：除了 shlex 切词，再用**原始空白切词**做二次扫描：

```python
raw_tokens = cmd.split()
for tok in raw_tokens:
    if re.match(r"^[A-Za-z]:[\\/]", tok):
        return f"命令含 Windows 绝对路径: {tok}"
```

**教训**：安全校验不要依赖任何会"规范化"输入的解析器。校验用的应该是原始字符串。

## 10. 绝对路径是分布外输入，模型会泄漏训练集路径

**现象**：对 `E:\xuexitongshuake\xxx` 这个真实路径，模型输出了 `data/tokenized`——那是**训练项目里的目录**。

**根因**：训练数据的路径全是相对路径（`build/app.log`）。绝对路径是分布外输入，模型退化成一件事：从上下文里抓最熟的片段。`data/tokenized` 是它见过最多的路径。

**修法**：壳层归一化——项目内的绝对路径改写成相对路径；项目外的直接返回 `--cwd` 用法提示，**根本不进模型**。

**教训**：小模型的"幻觉"往往不是编造，而是**记忆泄漏**。分布外输入会触发它去抓训练分布里最近的东西。

## 11. 短语级复读，`repeat_stop` 拦不住

**现象**：真实项目的 `find` 输出之后，模型开始反复写"目录里有 Eump，目录里有 Eump，…"，直到撞上 260 token 上限。

**根因**：已有的 `repeat_stop=16` 只检测**单 token** 连续重复。这里是"目录里有 Eump，"整个短语在循环，单 token 序列并不重复。

**修法**：`cut_phrase_loop()`，同一 3–48 字短语连续出现 ≥3 次就截断：

```python
_LOOP_RE = re.compile(r"(.{3,48}?)\1{2,}")
```

**教训**：退化有多种粒度。token 级、短语级、语义级要分别设防。

## 12. 陌生项目 + `--yes` = 幻觉写操作真实执行

**现象**：把模型指向一个真实项目，它看了一眼目录结构，第二轮幻觉出一个乱码路径的 `mkdir` 并**真的执行了**（因为测试时加了 `--yes`）。

**根因**：陌生项目的目录结构是分布外输入，模型陷入了"我看到目录→我应该建目录"的错误关联，参数还是乱码的。

**修法**：写操作用户确认不可省；`--yes` 只用于自己完全信任的场景。

**教训**：**给 Agent 写权限之前，先假设它会犯错。** 我们的默认行为是逐条确认，这不是麻烦，是底线。

---

## 13. 评测口径：多给一个可选参数被判定为错

**现象**：`read_head {"path":"build/app.log","lines":10}` 被判参数错误，因为标注里只有 `path`。

**根因**：比对时用了全参数严格相等。但 `lines` 是可选参数，模型给了默认值不算错。

**修法**：**只比必填参数**，可选参数多给忽略。

**教训**：评测口径比模型能力更容易出错。定义清楚"什么算对"再开跑，否则你优化的是一张错的表。

---

## 14. 同义改写让泛化变差（75% → 71%）

**现象**：为了提升口语泛化，往训练集里加了大量同义改写的指令（`_paraphrase` + 同义词表）。结果口语探针从 75% 掉到 71%。

**根因**：37M 的容量被多样表达**稀释**了。同一个意图有 20 种说法，每条见到的次数变少，反而学不扎实。

**修法**：回退到改写前的版本（`sft_r4`）。后来扩容到 62M，同样的问题自然消失。

**教训**：**加数据前先确认瓶颈是数据还是容量。** 容量不足时，更多样的数据会更糟。判别方法：加数据后同分布指标上升、泛化指标下降 → 就是容量问题，该扩容而不是加数据。

## 附：调试方法论

这个项目跑出来的几条通用经验：

1. **先看还原样本，再看 loss**。分词完打印一条 decode 结果，能提前发现 80% 的坑。
2. **loss 正常但输出乱 → 一定是标签/对齐问题**，不是模型容量。
3. **同分布 100% 但换说法就崩 → 是泛化问题**，先怀疑数据多样性，再怀疑容量。
4. **加数据后指标下降 → 容量不足**，别再堆数据。
5. **报错信息要当成产品功能**。早期失败信息不回灌，模型只会重复同样的错误调用；回灌真实 stderr 之后，它第二轮就能改参数。
6. **壳层能确定性解决的问题，不要指望模型学会**。路径归一化、循环截断、输出截断，三行代码 > 一百万 token。
